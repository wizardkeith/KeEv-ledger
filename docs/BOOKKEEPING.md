# Phase 2B1 local bookkeeping

Schema **v2** retains `local_profiles` from v1 and adds `accounts`, `categories` and `bookkeeping_transactions`. The committed v1/v2 Drift schema snapshots and generated migration verifier live in `drift_schemas/` and `test/generated_migrations/`. `LedgerDatabase.onUpgrade` creates only the new tables and history index for **v1→v2**; unsupported upgrades fail closed. Fresh installs use `createAll`. Both real file migration/reopen and schema verifier data-integrity tests preserve the v1 profile. Generate after table changes with `flutter pub run build_runner build` and `flutter pub run drift_dev make-migrations`.

`lib/features/bookkeeping/domain/` contains pure Dart Account, Category, BookkeepingEntry, BusinessDate and focused repository contracts. `application/BookkeepingService` creates accounts, categories, income and expense entries; lists history; derives balances; archives and tombstones. `data/` maps domain objects to Drift rows; it checks account ownership, status, currency, category nature and opening date in the same SQLite transaction as entry insertion. The Local Only profile is created independently; the existing shell and Add placeholder are unchanged. No default categories are seeded, so no language-specific names are frozen in SQLite. An explicit Phase 2B2 UI can supply localized defaults if approved.

Accounts: stable UUID, owning local profile, name, cash/bank/creditCard/eWallet/other kind, currency, signed opening minor units, business opening date, archive flag and UTC technical timestamps. Categories: stable UUID, owner, name, income/expense nature, archive flag and UTC timestamps. Entries: stable UUID, owner, account/category IDs, income/expense kind, strictly positive integer minor units, explicit matching currency, `yyyy-MM-dd` business date, optional note, UTC timestamps and nullable UTC deletion tombstone. History excludes deleted entries, sorts by business date descending then ID descending. No transfer rows or FX conversion are introduced. `Money` and `Currency` retain Phase 2A bounds and rules.

Balance = opening balance + active income − active expense, computed from persisted rows with `BigInt` intermediates and one checked conversion to supported `Money`. It is never stored separately; records survive restart. A credit-card opening balance can be negative (amount owed); purchases decrease the displayed balance. Card payments require a transfer and wait for Phase 2B2. Archived accounts/categories remain in history and cannot receive new entries; entry delete records a tombstone instead of dropping the row. Archive and deletion never cascade into history. The service rejects entries dated before the account opening date. Editing, unarchiving, credit-card payments, Quick Add and transfers remain deferred. SQLite is **not encrypted**; OS app sandbox is the current protection.

SQLite provides foreign keys, NOT NULL, stable primary keys and CHECK constraints. The repository additionally enforces relationships across account/category/profile/kind/currency under one transaction. `DriftLocalUnitOfWork` rolls back a multi-repository operation on typed `Failure` or exception. Domain/application layers import neither Drift nor Flutter. No new dependencies were introduced in 2B1.

## Phase 2B2 transfers and Quick Add

Schema **v3** adds one `transfers` row per business event with one stable ID, owner, source/destination account IDs, **both** positive integer-minor-unit amounts and currency codes, business date, optional note, UTC creation/update times and nullable UTC deletion timestamp. Foreign keys, account inequality, positive amounts and equal same-currency amounts have SQLite constraints. Account ownership, active status, opening dates and matching currencies are checked inside the repository's insertion transaction. It stores no FX rate: `LedgerTransfer.impliedSourceToDestinationRate` derives the exact reduced **destination major units per source major unit** rational from the two authoritative amounts. There is no implicit 1:1 conversion or network rate service. A transfer is always one atomic row; a failed write leaves no half-transfer, and `DriftLocalUnitOfWork` also rolls it back if a subsequent write fails. Deletion tombstones the entire event. The v2→v3 migration preserves all existing v2 rows, verified by on-disk migration/reopen and generated schema tests. Previously supported v1→v2 and direct v1→v3 paths remain available.

Balances now include outgoing **sent** Money as subtraction and incoming **received** Money as addition, each in its account currency. A bank→credit-card payment is a transfer, leaving the original card expense as the only expense. `BookkeepingService.historyEvents` merges each income/expense entry and transfer as **one event**, ordered by business date and stable ID. The History screen renders account direction, sent/received amounts, date and note; archived historical names remain available. No editable transfer UX is added.

Quick Add opens from the existing central Add action and Home button. The amount-first form creates income, expense or transfers through the application service; cross-currency transfers require an explicit received amount while same-currency transfers request it once. A new Local Only user can create an account and category inside the flow (default account opening balance zero, opening date today). Manual account currency and type selection is available; no account login or cloud service is needed. The strict `MoneyInput.parsePositive` accepts only decimal text within currency precision and integer range, never parses an authoritative `double`. Save completion follows SQLite commit, with in-flight tap protection and a typed-error message. Full account settings, transfer editing, batch changes and report/budget features remain deferred. Flutter widget tests use in-memory SQLite **only in tests**; production uses the local SQLite file.
