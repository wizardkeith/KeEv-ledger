# Trusted billing backend — Phase 8B-A

The `verify-purchase` and `refresh-entitlements` Edge Functions require a valid user JWT. They call Supabase Auth `getUser`, derive the account UUID from that result, and use the server-only service role for narrow billing RPCs. Both function routes explicitly retain `verify_jwt = true`. A client account ID is only a correlation check. A live store proof never grants Premium in Flutter.

`202609240001_billing_verification_v1.sql` creates private purchase identity/token and audit tables. The sanitized `billing_entitlements` table grants own-user SELECT only; authenticated clients cannot write it. The service-role-only commit RPC locks the store identity and Apple original transaction ID, prevents reassignment to another user, writes the verified source and recomputes both `premium` and `adFree` in one database transaction. An acknowledgement RPC updates Play state after the entitlement commit. Two active stores can independently protect one account's effective entitlement. Expiry is re-evaluated on every backend entitlement refresh; scheduled refresh/notifications remain 8B-B.

Apple uses pinned `@apple/app-store-server-library@3.1.0` for chain-validated JWS and App Store Server API current subscription status. Apple root certificates are server secrets in Base64 DER, sourced from [Apple PKI](https://www.apple.com/certificateauthority/); do not copy an incoming JWS `x5c` as a root. Bundle ID, environment, App Apple ID in production, product allow-list, current original transaction and `appAccountToken` are validated. Root rotation and actual Deno Edge compatibility must be verified before any sandbox or production enablement. The upstream Node library has had a Deno compatibility issue; no fallback decoder or unverified JWS path is present.

The chosen status item's `signedRenewalInfo` is verified with that same root-anchored `SignedDataVerifier`; original transaction, environment, approved current/next products and any renewal account token are checked. Billing Grace Period uses verified `gracePeriodExpiresDate` as the entitlement end even if the paid transaction has expired. Missing grace evidence is retryable without overwriting the previous source; invalid signature is rejected. Active with auto-renew off remains `cancelledButActive` until paid expiry. Billing retry alone and expired grace do not grant access; revocation overrides both. A submitted historical Apple transaction must match its own ID/product, while a current approved product in the same original transaction chain may differ after upgrade or downgrade.

Google uses a server-only service-account OAuth assertion and `purchases.subscriptionsv2.get`; the configured package and approved product/base plan, token, `externalAccountIdentifiers.obfuscatedExternalAccountId`, status and expiry are checked. Only a verified entitled state can proceed to backend `purchases.subscriptions.acknowledge`. When the acknowledgement call fails after durable entitlement commit, the private source remains `acknowledgement_pending`; a repeated verification retries. Play test purchases are rejected in a production backend. Google on-hold/paused/billing retry do not grant capabilities; grace and cancelled while paid do until store expiry.
For RTDN and periodic recovery, multiple approved line items are ordered by store expiry; client-initiated verification still requires the requested product's matching approved line. Exercise replacement/base-plan transitions with real Play test fixtures before checkout opt-in.

Store environment isolation is symmetric: `BILLING_ENVIRONMENT=sandbox` accepts only Play responses carrying `testPurchase`; `production` rejects those responses. An out-of-app re-subscription may carry a prior account hint under `outOfAppPurchaseContext.expiredExternalAccountIdentifiers`, but ordinary client verification never uses that fallback. The notification recovery flow verifies the old token's server-side binding before using the hint. Every configured `BILLING_PREMIUM_PRODUCT_IDS` product currently maps server-side to both `premium` and `adFree`; no capability claim from Flutter is accepted.
For an already registered Play token, its immutable server account binding can supply identity if a later current-state API response omits external identifiers. A new token without an ordinary account identifier needs a verified prior-token binding in the approved out-of-app context; otherwise it remains unresolved without entitlement.

The Flutter purchase listener persists verification material in its secure journal, awaits the trusted response and only then completes a transaction. Play local completion is held while backend acknowledgement is pending. A completion failure keeps the journal entry. Startup/account switch refresh fetches server state; a temporary outage can only use the Phase 8A bounded verified cache. Production `purchaseEnabled` stays `false`. App Store Server Notifications V2, Play RTDN, periodic reconciliation and production checkout are reserved for Phase 8B-B.

## Phase 8B-B provider events and missed-event recovery

Apple `apple-store-notifications` accepts only V2 `signedPayload`, verifies the outer JWS and any nested transaction/renewal JWS with the pinned Apple library and trusted roots, then records `notificationUUID` before querying current subscription status. Google `google-play-rtdn` validates Pub/Sub OIDC with pinned `jose@6.1.3`, Google's official JWKS, issuer, expiration, exact configured audience/service-account email and `email_verified`. Its `messageId` is deduplicated; `notificationType` never sets entitlement. It queries `subscriptionsv2.get`. Both external functions have `verify_jwt=false` individually; the user verification/refresh functions retain JWT checks.

Migration `202609240002_billing_notifications_v1.sql` adds a private event lease (two-minute stale recovery), bounded 25-source periodic claims and a source observation timestamp. `billing_commit_verification_v2` rejects older/equal observations under an account advisory lock before recomputing all valid Apple/Play sources. Client roles cannot access provider events or private tokens; the old service-role commit grant is retired. Event records contain only sanitized identities/type/fingerprint, no JWS, token or RTDN body. Retain event IDs for idempotency and support; an owner-reviewed retention schedule may prune them after a suitable audit period (proposed 400 days), but no deletion is scheduled here.
If a client verification's store observation loses this ordering race, it receives a retryable result and retains the pending journal; it does not retire an unacknowledged Play update from an older read.

`billing-reconcile` is a server-only endpoint guarded by a long random `BILLING_RECONCILE_SECRET` Bearer token. Schedule it **hourly** through trusted infrastructure; one invocation claims at most 25 due sources. Active/grace/retry/hold/cancelled/pending sources are refreshed roughly every six hours, pending Play acknowledgements in 15 minutes; a crashed batch is eligible after 20 minutes. Monitor backlog and invoke more bounded pages if growth warrants it. Store the scheduler credential in a managed secret store (Supabase Vault or equivalent), not public SQL or mobile code. The schedule is OWNER ACTION REQUIRED. Notifications and reconciliation use the same Apple/Google store adapters and server entitlement commit. Production checkout defaults off behind `PURCHASES_ENABLED=false`.
