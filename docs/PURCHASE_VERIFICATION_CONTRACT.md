# Purchase verification contract — Phase 8B-A

`POST /functions/v1/verify-purchase` uses the current Supabase JWT (never a user ID supplied as authority). Body: `platform` (`apple`/`google`), `transactionId`, `productId`, `proof` (Apple signed transaction data or server-verifiable transaction reference; Google purchase token), `accountId` (correlation UUID), and `packageId` for Play. The server allow-list and current store API determine validity and capabilities. Response: `outcome` = `VERIFIED_ACTIVE`, `VERIFIED_INACTIVE`, `PENDING`, `REJECTED`, `ACCOUNT_MISMATCH`, or `TRANSIENT_FAILURE`; `accountId` from Auth; sanitized `entitlement` (`active`, `premium`, `adFree`, `validUntil`, `verifiedAt`); `acknowledgementPending` for Play. The response contains no raw proof or token.

`POST /functions/v1/refresh-entitlements` uses the current JWT and no account ID. Response: `outcome: OK`, authenticated `accountId`, sanitized entitlement. The server re-evaluates source expiry and multi-source capability using server time on each refresh. A transient error never creates a new entitlement. `billing_commit_verification_v1` and acknowledgement RPCs are service-role-only and cannot be called by a mobile session.

Apple source identity is the verified original transaction ID, scoped by environment. Google source identity is the SHA-256 purchase-token fingerprint, scoped by environment; raw token stays private for future server refresh. Immutable account binding is enforced under a database advisory lock and unique store identity. Verified active/grace/cancelled-but-paid grants capabilities until store expiry; on-hold, billing retry, paused, pending, expired and revoked do not. A failed Play acknowledgement after durable grant keeps `acknowledgement_pending` for retry.
For Apple grace, `validUntil` is the verified signed renewal `gracePeriodExpiresDate`, not the paid transaction expiry. An Apple subscription upgrade may change the current approved product while keeping the verified original transaction/account identity. For Google, the requested product must match the verified line item, sandbox requires `testPurchase`, and production excludes it. Missing Apple grace evidence returns a transient failure; a bad renewal signature is rejected.

Flutter stores proof before calling the server. Backend active/inactive decisions precede local `completePurchase`; transient/mismatch/pending do not finish. After a backend-acknowledged Play result, Flutter retires the local wrapper without calling the plugin's duplicate Play acknowledgement path. Apple invokes `completePurchase` after server processing. A failed Apple finish retains the journal; duplicate callbacks use the same transaction key. Phase 8B-B adds signed Apple Notifications V2, Play RTDN, periodic reconciliation and production checkout. No notification endpoint is present here.
